# THR008: Field of a Thread-Safe Class Is Not Private

| | |
|---|---|
| **Severity** | Error |
| **Reported by** | PostSharp.Patterns.Threading |
| **Message** | `Field "<Field>" cannot be public or internal because its declaring class "<Class>" has a threading model that requires private fields. Make the field private, or apply the [ExplicitlySynchronized] custom attribute to this field to opt out from this rule.` |

## Cause

Several threading models protect the state of an object by controlling its entry points: the public and internal methods and property accessors acquire a lock, or are dispatched to the thread of the object, before they access the fields. A field that other classes can access directly bypasses this control, so these models require the fields of the class to be private.

PostSharp reports THR008 for a `public`, `internal` or `protected internal` field of a class that has one of the following threading models:

* <xref:PostSharp.Patterns.Threading.SynchronizedAttribute>;
* <xref:PostSharp.Patterns.Threading.ReaderWriterSynchronizedAttribute>;
* <xref:PostSharp.Patterns.Threading.ActorAttribute>;
* <xref:PostSharp.Patterns.Threading.ThreadUnsafeAttribute>, when run-time verification is enabled, which is the default in the debug configuration.

The <xref:PostSharp.Patterns.Threading.ThreadAffineAttribute> model does not require private fields. Protected fields are not reported.

## Resolution

* Make the field private, and expose it through a property or methods, whose accessors are entry points that the threading model controls. An automatic property is the shortest way, because its backing field is private.
* When your code synchronizes the access to the field by itself, apply the <xref:PostSharp.Patterns.Threading.ExplicitlySynchronizedAttribute> custom attribute to the field. PostSharp then neither reports the field nor checks the accesses to it.
